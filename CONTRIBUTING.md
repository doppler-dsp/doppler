# Contributing to doppler

The short version: **C first, and jm writes the rest.** Every algorithm
lives in the C library exactly once. The Python binding — the CPython glue,
the `.pyi` stub, `__init__.py`, the CMake wiring and the C test and
benchmark skeletons — is generated by
[just-makeit](https://just-buildit.github.io/just-makeit/) (jm) from a
declaration in `objects/<obj>.toml`. You write the declaration and the C
core; jm writes the binding.

See [CLAUDE.md](CLAUDE.md) for the design philosophy and the
[contributor guides](docs/dev/contributing/) for the detail behind every
step below.

## Setup

```sh
make setup   # one time per clone: sync dependencies, install the git hook
make help    # every target, generated from the Makefile, never stale
```

**Drive everything through `make`.** That includes jm: the pin lives in
`just-makeit.toml` (`jm_version`), the `jm-*` targets sync the pinned
version before they run it, and `make jm-pin JM=<x.y.z>` moves the pin
everywhere and re-locks. Never `uvx just-makeit` — it reuses whatever jm
happens to be installed as a uv tool, which drifts per machine. The one
exception today is jm's authoring verbs (step 1 below), which have no make
target yet.

## Git workflow

Every change to `main` goes through a branch and a PR, the release
version bump included. **The policy (how to shape a change, prove it, merge
it, and release) is [How We Work](docs/dev/workflow.md).** In short: one
change per PR, run the full matrix on every PR, merge on green by rebase,
and stop the line when `main` goes red.

### Branch naming

| Prefix   | Use                               |
| -------- | --------------------------------- |
| `feat/`  | new algorithm, module, or binding |
| `fix/`   | bug fix                           |
| `docs/`  | documentation only                |
| `chore/` | tooling, CI, deps, version bump   |
| `ci/`    | CI workflows and the CI image     |

```sh
git fetch origin && git checkout -b feat/cic-compensator origin/main
# ... implement, test ...
gh pr create --fill
gh pr merge --rebase   # once `CI passed` is green; deletes the branch
```

### What a PR must carry

A branch that changes code (`src/`, `native/`, `objects/`, `ffi/`) is held
by two gates in `make lint`:

- **A changelog entry** — one file, `changelog.d/<section>/<slug>.md`,
    where `<section>` is `added`, `changed`, `fixed`, `removed`,
    `breaking`, `deprecated` or `security`. The format is in
    [changelog.d/README.md](changelog.d/README.md); `make changelog-check`.
- **An issue statement in a commit message** — `Closes #N` (or `Fixes` /
    `Resolves`), or a `No-issue: <reason>` trailer when it genuinely closes
    nothing. Silence fails; `make issue-link-check`.

## Adding an object: the jm flow

The whole flow is six steps, and only step 4 needs algorithm knowledge.
The worked example is the real `MovingAverage` in `doppler.filter`
(component `boxcar`); every path below exists in the tree.

### 0. Characterize

Pick the shape first; it decides the declaration. A per-sample object
gets both `step` and `steps` — `step` is what lets a feedback loop use it.

| shape                                 | verb      | jm form              |
| ------------------------------------- | --------- | -------------------- |
| per-sample, small state, loop-usable  | `step(s)` | the default object   |
| block I/O: decimator, FFT, correlator | `execute` | `--preset blockwise` |
| event-driven: output decoupled        | `push`    | `--preset blockwise` |
| void input, array out: NCO, LO, PN    | `steps`   | `--preset generator` |

Why each shape gets its own verb:
[Adding a Module](docs/dev/contributing/adding-a-module.md), Step 0.

### 1. Declare the interface — `objects/<obj>.toml`

The manifest fragment is the source. This is `objects/boxcar.toml`,
trimmed:

```toml
[boxcar]
arg_type = "float _Complex"     # step()/steps() input
return_type = "float _Complex"  # step()/steps() output
no_state = "true"               # the state struct is hand-written in C
class_name = "MovingAverage"
serializable = "true"           # generate state_bytes/get_state/set_state
fragment = "generated"          # jm owns the binding fragment outright

[[boxcar.init_params]]
name = "len"
type = "size_t"
default = "4"

[[boxcar.properties]]
name = "gain"
type = "double"
writable = true
```

Write the fragment by hand, or let jm's authoring verbs write it
(`object`, `method`, `property`, `function`, and the `--preset` forms).
No make target wraps those verbs yet
([#2449](https://github.com/doppler-dsp/doppler/issues/2449)), so the
make-SSOT hook stops a bare call. Until it lands, run the pinned binary
(which `make jm-apply` syncs into `.venv`) with the hook's
deliberate-exception prefix, then apply:

```sh
MAKE_SSOT_OK=1 .venv/bin/just-makeit object myobj --module mymodule \
  --state gain:double:1.0 --mutable
make jm-apply
```

The recipe for each shape is in
[Adding a Module](docs/dev/contributing/adding-a-module.md), Step 1; the
full key reference is the
[jm docs](https://just-buildit.github.io/just-makeit/).

### 2. Register it in `just-makeit.toml`

```toml
[module.filter]
objects = ["fir", "boxcar"]
```

A new module also takes a `doc` key, which becomes its docstring on both
the runtime and the stub face.

### 3. Apply

```sh
make jm-apply
```

This syncs the pinned jm and regenerates everything the manifest owns.
For a new object it also creates the hand-owned stubs once:

| file                                        | owner                     |
| ------------------------------------------- | ------------------------- |
| `native/inc/doppler/boxcar/boxcar_core.h`   | **you** (created once)    |
| `native/src/boxcar/boxcar_core.c`           | **you** (created once)    |
| `native/tests/test_boxcar_core.c`           | **you** (skeleton)        |
| `native/benchmarks/bench_boxcar_core.c`     | **you** (skeleton)        |
| `native/src/filter/filter_ext_boxcar.c`     | jm (`/* jm:generated */`) |
| `native/src/filter/filter_ext.c`            | jm                        |
| `native/src/{boxcar,filter}/CMakeLists.txt` | jm                        |
| `src/doppler/filter/filter.pyi`             | jm                        |
| `src/doppler/filter/__init__.py`            | jm                        |

`make jm-apply` syncs the dev group without the project, which removes the
editable `doppler-dsp` from the venv: run `make pyext` before the next
Python test. Read the diff after every apply — it is how you confirm the
manifest change did what you meant.

### 4. Implement the C core

Fill in the state struct in `native/inc/doppler/<obj>/<obj>_core.h` and
the algorithm in `native/src/<obj>/<obj>_core.c`: `create`/`destroy`/
`reset` and the method bodies. No Python headers here.

**Write the docstrings in the header.** Its Doxygen is the source of the
Python docs: `@brief` becomes the summary, `@param`/`@return` the numpy
sections, and a `@code … @endcode` block a runnable `Examples` doctest
(`make test-stubs` executes it). Never edit the `.pyi` — the next apply
overwrites it.
[Docstring Authoring](docs/dev/contributing/docstring-authoring.md).

**If the object has running state** (a phase, a delay line, an
accumulator), it must serialize: the C triplet `dp_<obj>_state_bytes`,
`dp_<obj>_get_state` and `dp_<obj>_set_state` in the core (every derived
symbol carries the `dp_` `c_prefix`; see `dp_boxcar_get_state` in
`native/inc/doppler/boxcar/boxcar_core.h`), and
`serializable = "true"` in the manifest so jm generates the Python face.
[Adding a Module](docs/dev/contributing/adding-a-module.md), Step 4b,
and [State Serialization](docs/design/state-serialization.md).

### 5. Build and test

```sh
make pyext                                     # build the extensions
make test                                      # C tests (ctest)
make test-python TEST_PATHS=src/doppler/filter/tests/test_boxcar.py
make test-stubs                                # the header @code doctests
```

C tests go in `native/tests/test_<obj>_core.c`; Python integration tests
in `src/doppler/<module>/tests/`. A serializable object is tested in both
harnesses: a C round-trip with `DP_STATE_ROUNDTRIP_TEST` from
`native/tests/dp_state_test.h`, and an entry in the Python matrix
`src/doppler/tests/test_state_serialization.py`.

### 6. Reconcile and commit the declaration

Changed the manifest after the first apply? Apply again, then run the
gate CI runs:

```sh
make jm-apply
make drift-check
```

A header change also changes the generated C API pages: regenerate them
with `make gen-c-api`, which uses CI's doxygen if yours matches and
otherwise the CI image (so it needs docker). The `gen-c-api-drift`
pre-commit hook runs `make gen-c-api-check` on any staged `native/` C
file.

Commit the fragment, the C core and the tests together with whatever jm
regenerated. **Never hand-edit a jm-owned file** to fix a binding: change
the manifest (or the header, for docs) and re-apply, or the drift gate
goes red.

## Rust FFI binding

jm emits CPython only, so `ffi/rust/` is **maintained by hand** against
the C ABI: raw `extern "C"` declarations in `ffi/rust/src/lib.rs` and a
safe wrapper per object (`ffi/rust/src/fir.rs`, `nco.rs`, …) that owns
the handle and calls `*_destroy` in `Drop`. Keep it thin — the logic stays
in C — and keep its docs parallel to the header.

```sh
make test-rust
```

## Build commands

| Command            | What it does                               |
| ------------------ | ------------------------------------------ |
| `make help`        | **every** target — generated, never stale  |
| `make build`       | cmake configure + build (Release)          |
| `make pyext`       | Build the Python C extensions in place     |
| `make test`        | CTest (C tests)                            |
| `make test-python` | pytest, the same selection CI runs         |
| `make test-rust`   | Rust FFI tests (`cargo test`)              |
| `make jm-apply`    | Regenerate jm-owned glue from the manifest |
| `make drift-check` | jm manifest drift gate (what CI runs)      |
| `make docs`        | Build the documentation site               |
| `make lint`        | Every gate CI runs                         |
| `make gates`       | Debug a CI red only — never before CI      |

Testing is CI's job; `make gates` reproduces CI's whole gate set locally
and exists only to debug a CI red
([How We Work](docs/dev/workflow.md#2-prove-it-locally-then-push)).

## Code style

| Language | Tool           | Config                           |
| -------- | -------------- | -------------------------------- |
| C        | `clang-format` | `.clang-format`                  |
| Python   | `ruff format`  | `pyproject.toml`'s `[tool.ruff]` |
| Rust     | `rustfmt`      | `rustfmt.toml`                   |

`make format` runs the formatters, and `make lint` checks them, at the
versions `uv.lock` pins. Do not run them through `uvx`: it resolves an
unpinned release, which can format differently from CI. jm formats the C
it generates with the same pinned `clang-format`, so generated and
hand-written code agree.

Line width: **79 characters** across all languages.

## Gotchas

**Build artifacts stay out of the source tree.**
Always `make build` (outputs to `build/`).

**Thin means thin.**
A binding never reimplements C logic. If a behavior cannot be declared in
the manifest, the fix belongs in the C core or upstream in jm — not in a
hand-written wrapper.

**Never redefine wire formats.**
One `dp_header_t`, one magic value, one framing convention.
Don't define custom structs for data that crosses the C boundary.
